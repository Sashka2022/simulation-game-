# משלחות פתוחות ומשתתפות מרובות

## התנהגות המוצר

חמש משלחות קבועות; אין בדיקה שמגבילה מספר משתתפות במפגש או במשלחת. גם משלחת של משתתפת יחידה פעילה. פתיחת מפגש ו־QR קבוע אינם משתנים בעקבות נעילת הצטרפות, אישור או מעבר שלב. הצטרפות מותרת עד סיום המפגש, גם כשהמשחק כבר התחיל.

הצטרפות: קוד/QR ← שם או כינוי ← חמישה כרטיסים עם ספירות ← כניסה. ברירת המחדל היא כניסה מיידית ללא חשבון או אישור. ספירות במסך ההצטרפות מתרעננות כל שמונה שניות. כשמצב אישור מופעל, המשתתפת ממתינה עד שהמנחה מאשרת אותה; אישור אינו מסיר משתתפות אחרות.

במסך המנחה, ״ניהול משתתפות״ זמין בכל שלב: רשימה לפי משלחות, חיבור/ניתוק, הוספה ידנית לרשימה, הסרה, העברה ומינוי נציגה. הוספה ידנית מיועדת למשתתפת ללא מכשיר ואינה יוצרת הרשאת כניסה או נציגת הגשה. לכניסה ממכשיר משתמשים בקישור המפגש. אפשר לנעול הצטרפות ומעברים בנפרד ולדרוש אישור; כיבוי מצב אישור חל על מצטרפות חדשות ואינו מאשר אוטומטית בקשות ממתינות.

מסך המשתתפת מציג את האירוע והמשימה, שם המשלחת, רעיון אישי ומצב ההצעה הרשמית. רשימת רעיונות, חברות ובחירת נציגה ומעבר משלחת נמצאים באזורים נפתחים. כרטיס התפקיד, הסוד והעזרה נשארים בניווט הקבוע. טפסי הגשה ועריכת התחייבויות זמינים לנציגת ההגשה. אין פעולות ניהול למשתתפת רגילה.

משא ומתן ובדיקת מדיניות הן פונקציות שאפשר לבחור דרך ״הפונקציה שלי״ או להקצות דרך המנחה, לכל מספר של חברות. אפשר לבחור אחת מהן או את שתיהן; ברירת המחדל היא שתיהן. אין חסימת פעולה לפי הפונקציה, כך שגם משתתפת יחידה יכולה למלא את שתיהן. המשתתפת הראשונה עם מכשיר נעשית נציגת הגשה אוטומטית; המנחה או חברות המשלחת רשאיות להחליפה. המנחה יכולה להגביל את המינוי לעצמה. אם נציגה עוזבת/מוסרת, המערכת מקצה נציגה קיימת אחרת, אם ישנה. החלפה אינה פותחת מחדש הצעה רשמית שכבר הוגשה.

## נתונים והרשאות

- רשומת חברות נפרדת לכל דפדפן ומפגש: token מגובב, שם/כינוי, משלחת נוכחית, אישור, נוכחות, פונקציה וטיוטה אישית. הרשאה ב־HttpOnly cookie ל־30 יום; זהות אינה מבוססת על השם, ושמות כפולים מותרים.
- מצב המפגש כולל הגדרות, נציגה אחת לכל משלחת, גרסת שינויים ורעיונות עם מחברת, משלחת ושלב.
- PostgreSQL: הסרת האינדקס הייחודי הישן `(room,role) WHERE approved`, הוספת `name`, ‏`manual` ו־`focus` באופן חוזר ובטוח. נתונים קיימים נשמרים. SQLite מקבל עמודות תואמות וקבלות פקודות.
- בכל קריאה/פקודה ההרשאה נגזרת מחברות עדכנית בשרת. מעבר מאפס טיוטת שרת ומסיר גישה לסודות, לרעיונות ולנתוני חקירה פרטיים של המשלחת הקודמת. בקשת טיוטה/הגשה מתור ישן נבדקת גם מול `roleScope` ונדחית אחרי מעבר. טפסים וטיוטות מקומיות מתאפסים כשלקוח מקבל שיוך חדש.
- המשתתפת מקבלת רק את רשימת חברות המשלחת שלה ואת רעיונותיה; המנחה מקבלת את כולן. הצעות רשמיות, הסכם, עמדות להסכם ומידע שהמשלחות פרסמו במפורש הם מידע משותף. המקרן אינו מקבל שמות, רעיונות או חברות.
- הרשאות בשרת משתנות בעסקת המעבר עצמה. לקוחות מחוברים מציגים את העדכון בקריאה הבאה, בדרך כלל בתוך כשתי שניות. אי אפשר למחוק מזיכרונה של משתתפת סוד שכבר קראה או צילום מסך; אין התחייבות כזו.
- חיבור מחדש ורענון באותו דפדפן שומרים על החברות. ניסיון הצטרפות נוסף עם cookie תקף מחזיר אותה חברות. ניקוי cookies, גלישה פרטית חדשה או מכשיר חדש אינם מזהים אדם ללא חשבון; המנחה יכולה להסיר כפילות ידנית.

## מניעת התנגשויות

כל שינוי חברות/רעיון/נציגה וכל פקודת משחק מתבצעים תחת נעילת חדר באותה עסקה. מינוי נציגה בודק גרסת חברות כדי ששתי בחירות מקבילות לא יחליפו זו את זו בלי הודעה. הרשאה לנציגה נבדקת מחדש בעת כל פקודת משחק רשמית. מנוע המשחק מסרב להצעה שנייה לאותה משלחת ואותו סבב, גם עם UUID חדש, נציגה חדשה או גרסת משחק עדכנית. ניסיון חוזר עם אותו UUID מחזיר את הקבלה הקודמת בלי להגיש מחדש. רעיונות פנימיים אינם משנים את גרסת המשא ומתן ואינם מתנגשים בטיוטות או בהצעה רשמית.

## תשתית וקיבולת

אין מגבלת משתתפות עסקית; הקיבולת בפועל מוגבלת. הסנכרון הוא polling, לא WebSocket: ב־60 משתתפות פעילות, מנחה ומקרן צפויות בקירוב 31 קריאות מצב לשנייה, כ־111,600 בשעה, בנוסף להגשות. לכל מופע שרת עד שלושה חיבורי PostgreSQL; יש להשתמש בחיבור pooled של Neon. תורי פונקציות Vercel, מגבלות חיבור/CPU/אחסון/תעבורה של Neon, הרשת והמסלול החינמי עשויים להגביל ביצועים או ליצור חיוב.

קריאות מצב כוללות snapshot של המשחק. נפח ההסכם והרעיונות מצטבר; כתיבות לאותו חדר מסודרות בנעילה. הפעולות משנות רק את רשומות החברות שנפגעו. מעבר למפגש שנבדק, יש למדוד על הפריסה האמיתית, לעקוב אחר latency, שגיאות ותורי מסד, ולשקול מנגנון push ושמירת רעיונות בטבלה נפרדת. אין הבטחה לקיבולת אינסופית או ל־SLA על סמך בדיקה מקומית.

הגנת קצב: עד 240 פעולות כניסה/יצירה לדקה לכתובת IP, עד 240 בדיקות קוד לדקה ל־IP, ועד 120 פקודות לדקה לזהות בחדר. זו הגנת קצב ולא מכסת משתתפות; נוכחות אינה נחשבת לפקודת משחק. רשת בית ספר משותפת עלולה להגיע להגנה בגל הצטרפות גדול; אפשר להמתין דקה או לתאם הגדרות תשתית. המשתתפות נחשבות מנותקות אחרי כ־20 שניות ללא קריאת מצב; ״מחוברת״ אינה הוכחה שהיא קוראת או השלימה משימה.

## הרצת בדיקות

`npm run test:members` בודק SQLite מקומי. למסד בדיקות מבודד: `TEST_ADAPTER=postgres DATABASE_URL=… npm run test:members`. אין להריץ בדיקות על מסד ההפקה. התרחישים כוללים 5, 10, 20, 40 ו־60 זהויות, גדלים לא שווים, איחור, מעבר, נעילות, אישור, נציגה, טיוטות, ניסיונות חוזרים והגשות מקבילות. בדיקות הדפדפן מכסות ממשק, נגישות אוטומטית וניתוק/חיבור מחדש אמיתי. מספרי ביצועים ותוצאות הרצה מתועדים ב־validation.md.

`npm run test:migration` מיועד למסד בדיקות ריק ונפרד בלבד. הוא מסרב להשתמש במסד שכבר מכיל `hd_rooms`, יוצר בו את הסכמה הישנה ובודק מעבר לריבוי משתתפות תוך שמירת מפגש קיים.
